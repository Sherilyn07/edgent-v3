High-Level Design · Session Notes

Inside EdgentRAG v3

How a system that reads your documents and answers questions about them is put together — and why almost every decision in it comes from one rule.

For engineers new to distributed systems Reading time ~25 min Reference: github.com/abhaykes1/edgentrag-v3

01 What we are building

Start with the product, before any boxes and arrows.

A user signs in, uploads some files — PDFs, Word documents, plain text, even a video — waits while the system reads them, and then asks questions in plain English. The answers come back grounded in those specific documents, with a note saying which file each part came from.

That pattern has a name: RAG, short for retrieval-augmented generation. A language model on its own knows nothing about your files. RAG fixes that by doing two things in order:

  • Retrieval — find the handful of passages from your documents most likely to contain the answer.
  • Generation — hand those passages to a language model along with the question, and ask it to answer using only what it was given.

So the interesting engineering is not the model. It is everything around it: getting a 200-page PDF turned into searchable passages, finding the right four passages in milliseconds, and doing all of that without the user staring at a frozen screen.

Why version 3

Version 1 was one program on one server. Version 2 restructured the code so the slow parts ran separately. Version 3 keeps that code and changes where it runs — onto managed AWS services, so the system survives losing a process, a machine, or the GPU.

02 The one rule

Everything else in this document follows from this. If you remember one thing, remember this.

The API never does slow work.

Here is the problem it solves. Imagine the naive version: the browser uploads a 60-page PDF, and the server — in the same request — downloads it, extracts the text, splits it into passages, sends each passage to a GPU to be converted into numbers, and stores the results. Then it replies.

That request might take four minutes. Four minutes is long enough for a great many things to go wrong:

  • The browser gives up waiting and shows an error, even though the work is fine.
  • A load balancer between them closes the idle connection.
  • The server restarts, and the work simply vanishes — nobody wrote down that it had started.
  • Fifty users upload at once and the server holds fifty long-running requests, doing nothing else.

The fix is to make the API's job trivially fast: validate the request, write a row to the database, put a message on a queue, and reply. Milliseconds. Something else does the slow part, later, and reports back.

Once you accept that rule, most of the architecture writes itself. You need a queue. You need workers to drain the queue. You need somewhere to store progress so the browser can ask "is it done yet?". And you need a way to push updates back to a browser that is no longer holding a request open. Those four needs account for most of the boxes you are about to see.

03 Follow one upload

The clearest way to understand a system is to trace one thing through it end to end.

A user picks lecture-notes.pdf and clicks upload. Here is every step.

  1. The browser asks the API for permission to upload

    It does not send the file. It sends the filename and size. The API creates a database row for the file and replies with a presigned URL — a temporary web address that allows exactly one upload of exactly one file, expiring in an hour.

  2. The browser uploads straight to storage

    Using that URL, the file goes directly from the browser to S3, Amazon's file storage. The file bytes never pass through our API. This is why a 2 GB video works on a tiny server — the server only ever handled a filename.

  3. The browser tells the API "it landed"

    The API marks the session as processing and puts one message per file on the ingest queue. Then it replies. Total API time so far: a few milliseconds.

  4. An ingest worker picks up the message

    A separate program, running on a different machine, is continuously asking the queue "anything for me?". It takes the message, downloads the file from S3, and converts it to plain text.

  5. The text is cut into chunks

    A whole document is too big to feed a model, so it is split into overlapping passages of about 200 words — chunks. Each chunk remembers which file and which section it came from, so answers can cite a source.

  6. The chunks go into the database, and a job goes to the GPU

    Text first, deliberately. If everything after this fails, the text is still safely stored. The worker then queues an embed job for the GPU.

  7. The GPU turns each chunk into a vector

    An embedding is a list of 384 numbers that represents the meaning of a passage. Passages about similar things end up with similar numbers. This is what makes searching by meaning — rather than by keyword — possible.

  8. The vectors are written back beside the text

    A final short job writes the 384 numbers into the same database row that already holds the chunk's text. The file is marked done. When every file in the session is done, the session is marked ready.

Notice the shape

Every step ends. None of them waits for the next one. Each hand-off is a queue message, and a queue message is durable — if the worker dies at step 5, the message reappears and another worker starts step 5 again. Nothing is lost because nothing was only ever held in one program's memory.

04 Follow one question

Shorter, and latency matters here because a person is watching.

  1. The API records the question and queues it

    Two rows are written — the user's question, and a blank placeholder for the answer — and a message goes on the chat queue. The API replies immediately with the id of that blank answer.

  2. A chat worker turns the question into a vector

    The same embedding model that processed the documents now processes the question, producing 384 numbers in the same "meaning space".

  3. The database finds the closest chunks

    One SQL query compares the question's vector against every chunk's vector in that session and returns the four closest. "Closest" is measured by cosine distance — an angle between two lists of numbers.

  4. A prompt is assembled

    The four passages, the recent conversation, and the question are pasted into one block of text with an instruction: answer using only the context below; if it isn't there, say so.

  5. The language model answers, and the answer travels back

    The answer is published to a live event channel so the browser sees it immediately, and written to the database so a user who closed their laptop can still find it later.

Step 3 is the part that changed most in version 3, and it is worth dwelling on. In version 2, the vectors lived in a separate search engine, so answering meant: ask the search engine for matching chunk IDs, then query the database to fetch the text for those IDs, then stitch the two together. In version 3 the vector and the text sit in the same database row, so it is one query. Fewer moving parts, and a whole category of bug — "I found a chunk ID but the text is missing" — becomes impossible.

Four programs we wrote, and the managed services they lean on.

A useful detail: the ingest worker's container image is 3.4 GB and the chat worker's is 116 MB — thirty times smaller. Ingest carries a heavy document-conversion library; chat needs none of it. Because they are separate programs, the interactive path stays small and starts fast. In version 2 these were one image doing both jobs, and everything paid the 3.4 GB cost.

Worth pausing on

Look at the database tables: sessions, files, chunks, messages. No users. Cognito owns the people; our database stores only an opaque user ID on each session, and every route checks "is this session yours?" before answering. Less code, and no password to leak.

06 Three ideas that make it work

If you understand these three, you understand the system.

Idea one — a queue is a promise, not a pipe

When a worker takes a message off an SQS queue, the message is not deleted. It becomes invisible for a while. Only when the worker finishes successfully and says "done" does it actually go away. If the worker crashes, the timer expires, the message becomes visible again, and somebody else picks it up.

That single behaviour is what makes the system survivable. Compare it with the naive design: a crashed server loses work silently. Here, a crashed worker loses nothing.

It also means every message might be delivered more than once, so every handler must be safe to run twice. In our system it is: chunk identifiers are predictable, and writing them uses an "insert or update" that produces the same result whether it runs once or five times.

Two queues, not one, for ingest and chat. Sharing them would put one person's fifty-file upload ahead of everybody's questions.

Idea two — the GPU asks for work, nobody calls it

This one surprises people. The natural design is for the backend to call the GPU: POST /transcribe, wait for the answer. That has three problems when the GPU is a Colab notebook: it needs a public address (which changes every restart), it needs credentials to read files, and a dropped connection loses the job.

So the arrow is turned around. The GPU calls us, repeatedly, asking: anything to do?

The GPU holds exactly one credential — a shared token that permits one thing: ask for a job. It cannot read a file, list a queue, or see another user's data. Each job it receives arrives with presigned URLs already inside it, so it can fetch its input and write its output without ever learning the storage bucket's name.

Idea three — a worker cannot talk to a browser, so Redis relays

The user wants live progress: converting… chunking… 40 chunks stored…. But the worker producing that progress is on a different machine from the API process holding the browser's connection. They will never be the same process.

So the worker publishes progress to a named channel in Redis. Whichever API process is holding that browser's connection is subscribed to that channel, and forwards whatever arrives down to the browser. This is publish/subscribe.

Publish/subscribe is deliberately unreliable: if nobody is listening, the message is dropped. That is correct here, because the database still records everything that matters. A user who was disconnected simply reloads and reads the answer from the database.

07 Where it all runs

The same four programs, placed on real infrastructure.

A few placement decisions worth explaining:

  • The API runs on virtual machines behind a load balancer so more can be added under load, and so losing one does not take the site down.
  • The workers run as containers that scale on a different signal entirely: how many messages are waiting per worker. Not raw queue length — fifty messages means something different with one worker than with ten.
  • The GPU is not in AWS at all. It is a Colab notebook, and it holds no cloud credentials. The broker pattern is what makes that possible.
The honest limitation

There is one GPU, and it does not scale. Every piece of AWS infrastructure here is sized to scale up to that ceiling, not past it. Saying so plainly is part of the design: a system that knows its own bottleneck is easier to reason about than one that pretends not to have one.

08 Five things that break quietly

Real failures from deploying this. Each one produces no error message pointing at the cause.

Trap 1 — the health check that takes everything down

A load balancer checks each server's health and removes unhealthy ones. If that check tests the database, then a two-second database blip fails every server at once, and the load balancer removes all of them. A recoverable hiccup becomes a total outage. The rule: a health check must test only what that one machine controls.

Trap 2 — three separate layers that each kill live updates

Live progress needs a connection held open for minutes while mostly idle. Three things independently assume an idle connection is a dead one: the web server buffers responses, the load balancer times out after 60 seconds, and the CDN caches. Each needs its own opt-out. Miss any one and updates silently stop — with nothing wrong in any log.

Trap 3 — the stripped header

A CDN removes most headers before passing a request on, including Authorization. Every signed-in request then fails at the edge with a permission error, while the backend is perfectly healthy. The test that catches it: send a deliberately invalid token. If the reply says "unreadable token" the header arrived; if it says "missing token" something removed it. Both are the same status code — so a test that only checks the status code tells you nothing.

Trap 4 — the upload that blames the wrong component

Browsers refuse to upload to a different domain unless that domain explicitly allows it. Forget to configure it on the storage bucket and every upload fails — with the app reporting "is the API running?". The API is running fine; the request never went there.

Trap 5 — success reported over failure

A deploy script ran docker push … | tail -3. The push failed, but a pipeline reports the last command's result — so the script printed "done" over a hard failure and nothing was uploaded. Verify at the destination, not from the exit code of the thing that claimed to write there.

The pattern across all five: the error message points somewhere other than the cause. That is what makes distributed systems harder than single programs — not that more goes wrong, but that what goes wrong is reported by a component that was working fine.

09 Glossary

Terms used above, in plain language.

Chunk
A passage of about 200 words cut from a document, small enough to fit in a prompt and specific enough to be a useful search result.
Embedding / vector
A list of 384 numbers representing the meaning of a piece of text. Similar meanings produce similar numbers, which is what lets you search by meaning rather than by keyword.
Queue
A durable list of pending work. A consumer takes a message, the message goes invisible rather than being deleted, and it is only removed once the consumer confirms success.
Worker
A program whose whole life is: ask the queue for work, do it, confirm, repeat. It listens on no port and can be reached by nothing.
Presigned URL
A temporary web address carrying a signature that grants one operation on one file until it expires. It lets a browser or an outside machine touch storage without holding any credentials.
Publish/subscribe
A messaging pattern where senders post to a named channel and every current listener gets a copy. Nobody addresses anybody directly, and if nobody is listening the message is simply dropped.
Idempotent
Safe to run more than once with the same result. Required of every queue handler, because queues may deliver a message twice.
Load balancer
A single public entry point that spreads requests across several servers and stops sending traffic to any that fail their health check.
